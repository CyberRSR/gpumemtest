# gpumemtest — стресс-тест видеопамяти GPU с обнаружением ошибок

Нагружает видеопамять NVIDIA GPU (целевая карта — GeForce RTX 4090, 24 ГБ GDDR6X),
проверяет каждое прочитанное 64-битное слово и пишет журнал одновременно в консоль
и в файл.

- Тестируется почти вся свободная VRAM: на RTX 4090 с подключённым монитором это
  около 21,5 ГиБ. Один полный цикл всех тестов занимает примерно 14 с, при этом
  перекачивается около 14 ТБ на скорости около 1 ТБ/с.
- Эталонная копия данных не нужна. Ожидаемое значение каждого слова вычисляется по
  его индексу или адресу, поэтому проверяется 100 % выделенной памяти.
- По каждой ошибке пишутся смещение и адрес, ожидаемое и прочитанное значение, XOR,
  номера сбойных битов и направление (1→0 или 0→1). Сбойное слово перечитывается,
  чтобы понять, записано ли в память неверное значение или сбой был при чтении.
- В итоговом отчёте: гистограмма сбойных битов, повторяемость по адресам, время
  первой ошибки, температура, мощность, частоты и причины их ограничения (NVML).
- Самопроверка `--inject N` намеренно портит биты и проверяет, что все сбои пойманы.

## Скачать

Готовый `gpumemtest.exe` для Windows x64 лежит в разделе
[Releases](https://github.com/CyberRSR/gpumemtest/releases/latest). Нужен только драйвер
NVIDIA с поддержкой CUDA 13.4 (R580+); CUDA Toolkit не требуется.

## Сборка

Нужны CUDA Toolkit (12.x/13.x) и Visual Studio с компонентом «Разработка классических
приложений на C++».

```bash
build.bat
```

Скрипт сам находит Visual Studio через vswhere, а nvcc — через `CUDA_PATH`. По умолчанию
код собирается под `sm_89` (RTX 40xx) плюс PTX для более новых GPU. Для другой карты
задайте архитектуру, например `set ARCH=-arch=sm_86` для RTX 30xx, затем `build.bat`.

Linux:

```bash
nvcc -O3 -std=c++17 -arch=sm_89 -o gpumemtest gpumemtest.cu -ldl
```

## Запуск

```bash
gpumemtest.exe
```

Без параметров тест идёт до Ctrl+C. Первое нажатие останавливает тест мягко, с итоговым
отчётом; второе завершает программу сразу. Итог дописывается в журнал и при закрытии
окна консоли.

| Команда | Что делает |
|---|---|
| `gpumemtest.exe -t 30m` | 30 минут (`90s`, `2h`, `1d`; число без суффикса — минуты) |
| `gpumemtest.exe -t 2h -q` | 2 часа; в консоли только итоги циклов, предупреждения и ошибки |
| `gpumemtest.exe -n 1 --inject 3` | самопроверка: 1 цикл, 3 внедрённых сбоя на тест, все должны быть пойманы |
| `gpumemtest.exe -T random,stress -t 1h` | только «греющие» тесты со случайными данными |
| `gpumemtest.exe -T all -t 4h` | все тесты, включая `fade` (удержание данных при простое) |
| `gpumemtest.exe --stop-on-error -t 8h` | ночной прогон до первой ошибки |
| `gpumemtest.exe -m 90%` / `-m 16000` | ограничить объём: процент свободной памяти или МиБ |
| `gpumemtest.exe -l D:\logs\run1.log` | свой файл журнала (по умолчанию `gpumemtest_ГГГГММДД_ЧЧММСС.log` в текущей папке) |

Полный список параметров: `gpumemtest.exe --help`.

Коды выхода: `0` — ошибок нет, `1` — найдены ошибки памяти, `2` — прервано ошибкой
CUDA или драйвера, `3` — неверные параметры.

## Тесты

| Имя | Что делает | Что ловит |
|---|---|---|
| `addr` | в каждое слово пишется его собственный адрес, затем инверсия | ошибки адресации (алиасинг, «слипшиеся» адресные линии) |
| `random` | случайные данные с новым seed, затем чтение → проверка → запись инверсии | сбои, зависящие от данных, помехи на шине |
| `walk1`, `walk0` | одиночная 1 (или 0) проходит все 64 позиции, у соседних слов позиции сдвинуты | залипшие биты и линии данных |
| `movinv` | moving inversions W(P) → R(P)W(~P) → R(~P)W(P) → R(P) на 8 шаблонах (0, шахматки разного шага, случайный) | залипания, связанные ячейки, ошибки переключения |
| `mod20` | шаблон P в каждом 20-м слове, вокруг дважды переписывается ~P | влияние соседних ячеек |
| `copy` | половины области копируются друг в друга (device-to-device) с проверкой | ошибки на пути копирования |
| `stress` | 64 полных прохода «чтение → проверка → инверсия» случайных данных | нестабильность под длительной нагрузкой и при нагреве |
| `fade` | запись нулей и единиц, N секунд простоя (`--fade-sec`), проверка; по умолчанию выключен | утечка заряда (retention) |

## Как читать журнал

Каждая строка: время, уровень (`INFO`, `PASS`, `WARN`, `FAIL`, `ERROR`) и сообщение.
Строки уровней WARN/FAIL/ERROR сразу сбрасываются на диск, поэтому сохраняются даже
при зависании драйвера или BSOD. Пример ошибки:

```
2026-10-28 12:55:18.503 [FAIL ] addr, loop 1: W/R address -> 2 bad word(s), flipped bits mask 0x0100400000000000
2026-10-28 12:55:18.503 [ERROR]   offset 0x00087942c8 (VA 0x1b1d3942c8, chunk 0 word 17770585): expected 0x0000001b1d3942c8 read 0x0100001b1d3942c8 xor 0x0100000000000000 [1 bit: 56; 1->0 x0, 0->1 x1] | re-read same -> persistent (stored wrong)
```

Результат повторного чтения:

- **persistent**: в памяти лежит неверное значение. Если оно повторяется по одному и
  тому же смещению из цикла в цикл, это дефект ячейки.
- **transient**: при повторном чтении значение верное, значит, ошибка возникла на
  пути чтения. Типично для нестабильного разгона, перегрева или проблем питания.
- **unstable**: при повторном чтении получено третье значение.

Как отличить дефект от нестабильности:

- Ошибки по одним и тем же адресам и битам (`Failing addresses`, `Failing bits` в
  итоге) указывают на дефект памяти.
- Ошибки по случайным адресам, которые появляются после прогрева (время первой
  ошибки), указывают на нестабильность.

Смещения считаются от начала тестируемой области и стабильны в пределах одного
запуска. Это не физические адреса чипов: NVIDIA их не раскрывает.

## Особенности Windows и RTX 4090

- **Бюджет видеопамяти WDDM.** Если процесс занимает больше бюджета, который Windows
  ему выделила, менеджер видеопамяти начинает вытеснять блоки в ОЗУ и подкачивать их
  обратно. Тест тогда замедляется на треть, а часть данных ходит через PCIe вместо
  VRAM. Поэтому по умолчанию остаётся запас 1 ГБ (`--reserve`), объём выделения
  ограничивается бюджетом DXGI, а перед каждым тестом бюджет проверяется заново. Если
  Windows его урезала, тест освобождает блоки и пишет `WARN`.
- **Sysmem fallback.** Блоки, которые драйвер разместил в системной памяти, видны по
  скорости записи и исключаются из теста. Чтобы этого не было совсем, в Панели
  управления NVIDIA → «Управление параметрами 3D» установите для «CUDA — Sysmem
  Fallback Policy» значение «Prefer No Sysmem Fallback».
- **TDR (сторожевой таймер дисплея).** Каждый запуск ядра обрабатывает один блок
  256 МБ за доли миллисекунды, поэтому TDR не срабатывает даже на карте с монитором.
  Сброс драйвера во время теста (`CUDA error ...`, событие `nvlddmkm` в журнале
  Windows) под такой нагрузкой сам по себе признак нестабильности.
- **Монитор на тестируемой карте.** Рабочий стол может подтормаживать. Около 2,5 ГБ
  (рабочий стол, другие приложения и резерв) не тестируются. Для максимального
  охвата закройте браузеры и игры или подключите монитор к другому GPU.
- **ECC.** У RTX 4090 ECC можно включить в Панели управления NVIDIA. При включённом
  ECC одиночные ошибки исправляются аппаратно и тесту не видны. Чтобы видеть «сырые»
  ошибки, ECC должен быть выключен (тест предупреждает об этом).
- **Разгон памяти GDDR6X.** Ошибки передачи GDDR6X ловит EDC и повторяет передачу,
  поэтому нестабильный разгон часто проявляется не ошибками, а падением скорости. Тест
  показывает частоту памяти под нагрузкой (`Memory clock under load ... overclocked`),
  ГБ/с в каждой строке и долю от теоретического пика в итоге. Если при повышении
  частоты ГБ/с не растут или падают, либо появляется `WARN ... bandwidth dropped`,
  частота уже за пределом стабильности, даже при 0 ошибок.
- **Температура памяти.** Температуру GDDR6X (memory junction) NVML на GeForce не
  отдаёт; смотрите её в HWiNFO64 параллельно с тестом. В журнале — температура GPU,
  мощность, частоты SM/MEM и причины ограничения частот (power, thermal и т.д.).

## Файлы

- `gpumemtest.cu` — исходник (CUDA C++17, один файл).
- `build.bat` — сборка под Windows.
- `gpumemtest.exe` — собранная программа (sm_89 + PTX, CUDA 13.4).
